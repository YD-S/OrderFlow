# OrderFlow

An event-driven order processing system, built to learn microservices architecture and pub/sub messaging in Go by actually shipping something, rather than through tutorials.

It simulates a small e-commerce order pipeline: placing an order triggers a chain of independent services reacting to events, with no service ever calling another directly.

## Architecture

Four services, one message broker, one shared Postgres instance:

```
Client
  │  HTTP
  ▼
┌─────────────┐  order.created   ┌───────────────┐  inventory.reserved   ┌────────────────┐
│ Order        │ ───────────────▶│ Inventory      │ ─────────────────────▶│ Payment         │
│ (has an API) │                 │ (pure consumer)│                       │ (pure consumer) │
└─────────────┘                  └───────────────┘                       └────────────────┘
       ▲                                 │                                        │
       │        inventory.failed         │              payment.completed /       │
       └─────────────────────────────────┘              payment.failed            │
       ▲                                                                          │
       └──────────────────────────────────────────────────────────────────────────┘
                                                                                   │
                                                                                   ▼
                                                                        ┌────────────────┐
                                                                        │ Notification     │
                                                                        │ (pure consumer)  │
                                                                        └────────────────┘
```

Only **Order** exposes an HTTP API. Inventory, Payment, and Notification never receive requests, they run a consumer loop against a Valkey stream and react to whatever shows up. Order also consumes `inventory.failed` and `payment.failed` so a failure anywhere downstream can cancel the order, that's the saga / compensating-transaction piece.

### Why Valkey Streams instead of plain pub/sub

Plain `PUBLISH`/`SUBSCRIBE` is fire-and-forget, a subscriber that's down when an event fires just misses it, permanently. Valkey Streams (`XADD` / `XREADGROUP` / `XACK` / `XAUTOCLAIM`) gives persistence, consumer groups, and at-least-once delivery, a service that's redeploying when an event fires still gets it the moment it comes back up.

### Why each service is its own Go module

Every service under `services/` has its own `go.mod`. This isn't just organization, it's the actual enforcement mechanism: without a real module boundary, nothing stops one service from directly importing and calling another's internals, which would quietly defeat the entire point of routing everything through events. `internal/` folders handle the equivalent problem *within* a single service (keeping `api/`'s generated code out of `store/`'s reach, for example).

### Why hexagonal layering (api / service / store)

Each service splits into three layers:

- **`api/`** (Order only) — inbound HTTP, request validation, wire-format mapping. The only service with this layer, since it's the only inbound entry point.
- **`service/`** — pure business logic. Knows nothing about HTTP, Postgres, or the broker. Depends only on interfaces defined in its own `ports.go`.
- **`store/`** — outbound adapters: the Postgres repo and the broker publisher/subscriber.

All type conversion happens at the edges (`api/mapper.go`, `store/mapper.go`, generated by convgen), so `service/` never has to think about JSON tags or `pgtype` wrappers.

### Why one shared Postgres instance, separate schemas

Each service gets its own schema (`order_svc`, `inventory_svc`, etc.) and its own scoped database role that can only see its own schema. This is genuine isolation (grants, not just convention) at a fraction of the resource cost of four separate Postgres containers. `tern` tracks each service's migration history in its own schema-qualified version table so they never collide.

## Project layout

```
orderflow/
├── go.mod / go.sum          # root module — holds dev tool directives only, no app code
├── go.work / go.work.sum    # ties every module below together for local development
├── Taskfile.yml             # wires up the included taskfiles below
├── taskfiles/
│   ├── gen.yml               # sqlc + convgen
│   ├── migrate.yml            # tern, per service or all
│   └── docker.yml                # local stack up/down
│   └── release.yml               # create new release tag, bump versions, push to GitHub
│
├── events/                  # shared event contracts (OrderCreated, InventoryReserved, ...)
├── platform/
│   └── broker/                # generic Consumer[T] / Publisher, built on Valkey Streams
│
├── sql/                     # centralized SQL, one subtree per service
│   ├── order/{migrations,queries}/
│   ├── inventory/ ...
│   ├── payment/ ...
│   └── notification/ ...
│
├── services/
│   ├── order/                # the only service with an api/ layer
│   │   ├── api/                # huma handlers, routes, request/response types, mapper
│   │   ├── service/              # domain.Order, status transitions, ports.go
│   │   ├── store/                  # repo, mapper, publisher, sqlc output
│   │   ├── cmd/main.go               # fx.New(store.Module, service.Module, api.Module, ...)
│   │   └── Dockerfile
│   ├── inventory/             # pure consumer — same shape, minus api/
│   ├── payment/                # same shape as inventory
│   └── notification/            # same shape, no publisher (end of the chain)
│
├── docker-compose.yml
├── init.sql                 # creates schemas + scoped roles on first boot
└── sqlc.yaml                # root-level, one package config per service
```

## Tech stack

| Concern | Choice | Why |
|---|---|---|
| Language | Go | Consistent across all four services |
| Message broker | Valkey (Streams) | Persistence + consumer groups without Kafka's operational weight |
| Database | PostgreSQL | One shared instance, isolated by schema and role |
| Query layer | sqlc | Type-safe queries generated from SQL, no ORM |
| Migrations | tern | Per-service, schema-scoped version tracking |
| API layer | huma (+ chi via humachi) | Code-first: request validation and OpenAPI docs generated from Go structs, no hand-maintained yaml |
| Mapping | convgen | Compile-time generated conversions between api / domain / db representations |
| Dependency injection | Uber Fx | Declarative wiring, one `fx.Module` per layer per service |
| Local multi-module dev | Go workspaces (`go.work`) | Cross-module resolution without `replace` hacks |
| Dev tooling | Go 1.24+ `tool` directive | `task`, `tern`, `gograph`, `sqlc`, `convgen` all pinned in `go.mod`, no global installs |
| Task runner | Taskfile (go-task) | Namespaced, composable tasks (`gen:sqlc`, `migrate:apply`, `gate:check`) |

## Getting started

**Prerequisites:** Go 1.26+, Docker, Docker Compose.

```bash
git clone https://github.com/YD-S/OrderFlow.git && cd orderflow

# confirm the workspace picks up every module
go work use .   # only if `.` isn't already listed in go.work

# start Postgres + Valkey
go tool task docker

# apply migrations for every service
go tool task migrate

# generate sqlc + convgen output for every service
go tool task gen

# build and start all four services
go tool task docker
```

Once it's up, place a test order:

```bash
curl -X POST http://localhost:8080/orders \
  -H "Content-Type: application/json" \
  -d '{"customer_id":"...uuid...","items":[{"sku":"WIDGET-1","quantity":2}]}'
```

Then watch the event actually land in the stream:

```bash
docker exec -it orderflow-valkey-1 valkey-cli XRANGE orders:events - +
```

## Common tasks

| Command | Does |
|---|---|
| `go tool task gen` | Regenerate sqlc + convgen output for all services |
| `go tool task gen:sqlc` | sqlc only |
| `go tool task gen:convgen` | convgen only |
| `go tool task migrate` | Apply migrations for every service |
| `go tool task migrate:apply -- order` | Apply migrations for one service |
| `go tool task gate` | Rebuild the dependency graph and enforce boundary rules |
| `go tool task docker` | Build and start the local stack |
| `go tool task docker:down` | Stop the local stack |
